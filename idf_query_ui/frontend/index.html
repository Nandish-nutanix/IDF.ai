Evictable Entities

Indexing IS required. Evictable entities need is_index_column: true to support WhereClause, GroupBy, and Sort operations via r-indexed maps.

These entities are loaded on demand and evicted when not in use. Without indexing, queries on their attributes will not work.

Unevictable Entities

Indexing is NOT required for filtering. These entities are always resident in the memory cache — all attributes are searchable without explicit indexes.

Unevictable entities are always in the memory cache. Indexes here only consume extra memory without adding required filtering capabilities. If an index was added, ask the developer to remove it.

Testing IDF Changes

A definitive workflow for testing your changes to IDF on PC, PE, or AFS environments. Covers Config (schema/indices), Python Client, and Server binary deployment.

Verify index: Set CVM IP in header first
Config Changes
Python Client
Server Binary

Step 1: Edit Schema / Config

All config overrides (entity types, metric types, indices) must be placed in the following path on your target node:

~/config/insights/entity_attribute_config.proto

SCP your modified proto file to this path on each CVM in the cluster (or use allssh for multi-node).

Step 2: Whitelist GFlags for Testing

By default, gflags cannot be modified via the :2027 web UI. You must create a whitelist file first. This enables ALL flags for testing purposes:

echo '[".*"]' > /home/nutanix/config/insights_server_gflags_whitelist.json && \
curl http://127.0.0.1:2027/h/gflags?reload_whitelist=1

What this does: Creates a regex whitelist allowing all flags, then tells the server to reload it without restart.

Step 3: Apply Changes (Restart)

After modifying the config proto, restart insights_server across the cluster for changes to take effect:

allssh genesis stop insights_server && cluster start

Wait 10-15 seconds after restart, then verify your indices were created by visiting the index map stats endpoint (link at top of page).

Step 4: Verify

Confirm your entity types and indices are registered correctly:

curl http://<CVM_IP>:2027/index_map_stats
curl http://<CVM_IP>:2027/entity_type_stats

Important: Python Environment

The Python virtual environment is not fully populated by default in containerized or minimal CVM environments to save space. You must install dependencies first before running any IDF Python client scripts.

Step 1: Install Python Dependencies

Run the dependency installer script (only needed once per node):

bash /home/nutanix/bin/install-py3-deps.sh

This populates the venv with all required IDF Python packages (protobuf, grpc, etc.).

Step 2: Execute Your Script

Always use the specific virtual environment Python binary — do not use the system python3:

/home/nutanix/.venvs/bin/bin/python3.9 your_script.py

Replace your_script.py with the path to your test client. The venv binary ensures the correct protobuf and IDF client packages are on the path.

Tips

• Use allssh to run your script across all nodes if testing cluster-wide behavior.
• For interactive debugging, activate the venv: source /home/nutanix/.venvs/bin/bin/activate
• Check ~/data/logs/insights_server.log for server-side errors from your client calls.

Step 1: Build the Binary

C++ server binaries must be built via xgear from your development machine (viewtop). Build the insights_server target:

xgear make insights_server

This produces the binary at build/bin/insights_server in your workspace.

Step 2: Deploy to Target Node

SCP the built binary to the CVM, replacing the existing one:

scp build/bin/insights_server nutanix@<CVM_IP>:/home/nutanix/bin/insights_server

For multi-node clusters, repeat for each CVM or use a script to push to all nodes.

Step 3: Restart via Genesis

After replacing the binary, restart the service through Genesis:

allssh genesis stop insights_server && cluster start

Genesis will pick up the new binary on restart. Verify with curl http://127.0.0.1:2027/ to confirm the server is serving.

Debugging

• Logs: ~/data/logs/insights_server.log and insights_server.FATAL
• Core dumps: ~/data/cores/
• Check service status: genesis status or cluster status

Container Deployment & Image Generation

Developer workflow for building custom IDF container images and deploying them to an SMSP environment. Used for NCM, Objects, and LTSS deployments.

1

Custom Image Creation

Images are tagged by GBN (Global Build Number) and build-type under the registry path:

canaveral-legacy-docker/insights-server-chakr/<image-name>
Enter a branch and fetch its HEAD build number (resolved server-side via depsdb)

Build commands (run from your viewtop workspace):

# Install all Python dependencies for packaging
xgear make all_pydeps

# Package the Python egg
xgear make package-egg

# Build the Docker image
xgear make package-docker--insights-server-chakr

After building, push the image to your registry (Quay or JFrog Artifactory). Note your registry credentials for the deployment step.

2

SMSP Environment Deployment

Two supported methods for deploying to an SMSP cluster:

Quick manual deployment using mspctl and a YAML specification file:

mspctl application apply idf -u <smsp-cluster-uuid> -f <yaml-file-path>

Replace <smsp-cluster-uuid> with your target cluster UUID and point to your deployment YAML.

Production-standard deployment via Helm chart and the Service Manager API:

# 1. Launch a local chartmuseum (serves your Helm chart)
docker run -d -p 8090:8080 chartmuseum/chartmuseum --storage local --storage-local-rootdir /charts

# 2. Package and push your Helm chart
helm package ./idf-chart
curl --data-binary "@idf-chart-0.1.0.tgz" http://localhost:8090/api/charts

# 3. Deploy via Service Manager API
curl -X POST "https://{pc-ip}:9440/api/lifecycle/v4.0/svcmgr/applications" \
  -H "Content-Type: application/json" \
  -d @deployment-payload.json

The payload JSON should reference your chart repository URL, image tag, and any custom values overrides.

3

Container Debugging & Config Management

Managing gflags and debugging in a containerized IDF deployment:

Edit GFlags ConfigMap

In Kubernetes, gflags are stored in a ConfigMap. Edit it directly:

kubectl edit cm idf-gflags-config -n <namespace>

Restart Pod to Apply

After editing the ConfigMap, delete the pod to force a restart with the new config:

kubectl delete pod <idf-pod-name> -n <namespace>

Viewing Logs

Two options for viewing IDF container logs:

# Direct pod logs
kubectl logs <pod-name> -c idf -n <namespace>

# Follow logs in real-time
kubectl logs -f <pod-name> -c idf -n <namespace>

For aggregated logs across pods, use the Fluentd collector or your cluster's logging solution (e.g., Kibana/Elasticsearch).
